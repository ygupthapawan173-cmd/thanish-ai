# V100.1 — Voice & Wake Recovery candidate
Base: V100 consolidated integration candidate. Package ID unchanged; versionCode 101, versionName 100.1-wake-recovery-candidate.

Observed user symptom: notification remains Wake paused after toggling wake. Source audit found a lost-rearm risk: pause invalidated the scheduled epoch; rearm depended on later busy/settings flow emissions. The foreground Activity had no onStop voice cleanup, so a manual recognition or live session could hold the microphone after minimizing. These are plausible contributors, not a proven device root cause (no logcat supplied).

Changes:
- One pending rearm task per service; explicit cancellation; periodic 2.5 s idle-only watchdog to recover missed events without bypassing retry delays or stealing a mic lease.
- Preserve checks for consent, permission, privacy mute, owner verification, background conversation, microphone and TTS ownership.
- UI onStop cancels pending manual follow-up, acknowledgement, recognition, Live duplex and foreground TTS, without stopping the service's own background conversation. A foreground conversation ends when leaving the UI; a new wake phrase starts a service-owned turn.
- Recheck wake on resume; distinguish microphone busy, TTS busy, rearming and occupied lease in notifications. Avoid replacing active notification with loading on redundant service start. Close service preference listener on destruction.
- Track distinct engine instances as mic-busy owners rather than sharing the same label. Wake capture lease itself remains exclusive.
- No API provider, credentials, budget settings, model router, or offline model assets changed. Existing UI preserved. Locked-screen cloud/recognition privacy rules unchanged.

Verification performed locally: 1052 pure JVM checks (1024 eligibility combinations plus scheduler, lease and retry checks); 12 source integration guards; V47/V50/V100 source guards; desktop SQLite migration checks; previous V100 audio regression checks.
